## ADR-001: 顶层容器选择

**状态**: ✅ 已决定  
**日期**: 2026-06-08  
**决策者**: 产品 + 技术

### 背景

业务方需要 AI 平台支持多业务场景共存,每个场景需要独立的流程、助手、知识库。

### 考虑的选项

1. **AI 应用 (ai_app)**:类似 Jeecg-AI 原设计,AI 应用为顶层
2. **项目 (ai_project)**:Workspace 模式,项目为顶层
3. **混合模式**:平台 + 项目双层

### 决定

选择 **项目 (ai_project) 作为顶层容器**,直接包含流程(移除 ai_app 表)。

### 理由

- 业务场景天然隔离,数据安全
- 资源可独立管理(成员、API Key、Webhook)
- 多成员协作清晰
- 与 Jeecg-AI 概念差异化

### 后果

- ✅ 项目级资源隔离清晰
- ✅ 多租户友好(虽然本期不实现)
- ⚠️ 流程不再是独立单元,必须挂载到项目
- ⚠️ 原 ai_app 概念需要重新培训用户

## ADR-002: 移除 Redis/PostgreSQL 外部依赖

**状态**: ✅ 已决定  
**日期**: 2026-06-08  
**决策者**: 技术

### 背景

部署环境希望最小化,只装 JDK + MariaDB + Nginx。

### 考虑的选项

1. **保留 Redis + PostgreSQL**:成熟生态
2. **Redis 替代为 Caffeine,保留 PostgreSQL** 部分
3. **完全移除**:Redis → Caffeine,PostgreSQL → MariaDB + Hnswlib

### 决定

**完全移除**,Redis 用 Caffeine 替代,PostgreSQL+pgvector 用 MariaDB+Hnswlib 替代。

### 理由

- 单机部署,QPS 100+ 足够,Caffeine 性能足
- 嵌入式 Hnswlib 性能与 pgvector 相当
- 部署依赖从 5+ 减少到 3 个
- 运维成本降低
- 启动时间缩短

### 后果

- ✅ 极简部署
- ✅ 启动包小
- ⚠️ 不支持分布式部署(扩展需迁移)
- ⚠️ Caffeine 内存有限,需谨慎使用
- ⚠️ Hnswlib 单机索引,数据量大时需升级

### 升级路径

| 触发条件 | 升级方案 |
|---|---|
| Caffeine 缓存频繁淘汰 | 引入 Redis |
| Hnswlib 内存不足 | 迁移到 Milvus |
| QPS > 1000 | 多实例 + Redis |

## ADR-005: 向量库选择 Hnswlib

**状态**: ✅ 已决定  
**日期**: 2026-06-08  
**决策者**: 技术

### 背景

知识库需要向量检索,需要在不引入 PostgreSQL 的前提下选型。

### 考虑的选项

1. **pgvector** (用户原本推荐,但 PostgreSQL 被移除)
2. **Milvus** (专业级,但重)
3. **Qdrant** (Rust,性能好)
4. **Hnswlib** (Java 嵌入式,无服务)
5. **Chroma / FAISS** (Python 生态,Java 调用不便)

### 决定

**Hnswlib (jelmerk/hnswlib-core) 0.7.1**

### 理由

- Java 原生,无服务依赖
- HNSW 算法性能优异(亿级毫秒级)
- 文件持久化(.bin)
- 库成熟稳定

### 后果

- ✅ 零外部依赖
- ✅ 性能优秀
- ⚠️ 单机索引,不支持分布式
- ⚠️ 索引重建需停服或异步

### 升级路径

数据量 > 1000 万向量时,迁移到 Milvus(协议兼容)。

## ADR-006: 缓存方案选择 Caffeine

**状态**: ✅ 已决定  
**日期**: 2026-06-08  
**决策者**: 技术

### 背景

需要本地缓存替代 Redis。

### 考虑的选项

1. **Caffeine** (推荐)
2. **Guava Cache**
3. **EhCache**
4. **ConcurrentHashMap 手写**

### 决定

**Caffeine 3.1.8**

### 理由

- 性能最优(Java 缓存库 benchmark 第一)
- Spring Cache 集成
- 支持 LRU/LFU/TTL/WeakReference
- 社区活跃

### 后果

- ✅ 性能优异
- ✅ API 简单
- ⚠️ JVM 内存有限,需控制缓存大小
- ⚠️ 多实例间不同步(可接受)

**状态**: ✅ 已决定  
**日期**: 2026-06-08  
**决策者**: 技术

## ADR-010: AI 助手复用 Flow 机制

**状态**: ✅ 已决定  
**日期**: 2026-06-08  
**决策者**: 产品 + 技术

### 背景

AI 助手是核心能力,需要与流程系统协同。

### 考虑的选项

1. **助手复用 Flow**:`is_assistant=1` 标志
2. **助手独立实体**:新建 ai_assistant 表
3. **助手独立服务**:独立微服务

### 决定

**助手复用 Flow 机制**,`is_assistant=1` 标志 + `ai_assistant_*` 扩展表。

### 理由

- 共享流程引擎、触发器、版本管理
- 减少重复代码
- 用户体验一致(在流程列表中看到助手)

### 后果

- ✅ 基础设施共享
- ✅ 助手和流程统一管理
- ⚠️ `ai_flow` 表增加字段
- ⚠️ 助手特有配置(人设/工具)需扩展表

## ADR-011: 节点可自定义两层设计

**状态**: ✅ 已决定  
**日期**: 2026-06-08  
**决策者**: 产品

### 背景

业务流程需要支持自定义节点(企业级需求)。

### 决定的方案

**两层设计**:
- **开发者扩展**:写 Java 类 + Vue 组件
- **用户自定义**:UI 配置脚本/HTTP/SQL 节点

### 理由

- 覆盖 95%+ 场景
- 平衡灵活性和易用性
- 高级用户用代码,普通用户用 UI

### 后果

- ✅ 灵活性高
- ✅ 用户可零代码扩展
- ⚠️ 开发者扩展需重启服务(SPI 自动扫描)
- ⚠️ 用户自定义需 UI 复杂度足够

## ADR-012: UI 导航选择侧边栏

**状态**: ✅ 已决定  
**日期**: 2026-06-08  
**决策者**: 产品

### 背景

UI 主导航采用侧边栏还是顶部?

### 决策历程

| 时间 | 选项 | 决定 |
|---|---|---|
| 最初 | 侧边栏 | ✅ |
| 中途讨论 | 顶部导航(Notion 风格) | ❌(讨论后保留) |

- ✅ 实施快
- ✅ 用户熟悉
- ⚠️ 不适合非常深的多级菜单
- ⚠️ 占用 200px 横向空间

**状态**: ✅ 已决定  
**日期**: 2026-06-08  
**决策者**: 项目经理

## ADR-014: 部署方式选择传统虚拟机

**状态**: ✅ 已决定  
**日期**: 2026-06-08  
**决策者**: 技术

### 背景

部署环境选择?

### 考虑的选项

1. **Docker Compose** (单机容器化)
2. **Kubernetes** (生产级)
3. **传统虚拟机/物理机** (Nginx + jar)
4. **云托管** (阿里云/腾讯云)

### 决定

**传统虚拟机/物理机**(Nginx + jar + MariaDB),提供 Docker Compose 备用方案。

### 理由

- 用户指定
- 部署简单
- 运维要求低
- 适合内部使用

### 后果

- ✅ 部署简单
- ✅ 运维成本低
- ⚠️ 不支持自动扩缩
- ⚠️ HA 需要额外配置(keepalived)
